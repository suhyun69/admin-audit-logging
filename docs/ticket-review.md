# 작업·티켓 재검토 기록

일자: 2026-11-08. 대상: 구현 명세, 구현 계획, 에이전트 규칙, 브랜치 전략과 개별 티켓. orchestra 관점의 대조와 qa 역할의 독립 읽기 검토를 수행했다. 이 기록은 계획 검토이며 제품 테스트나 티켓 구현 승인이 아니다.

## 발견 사항과 반영

| 발견 사항 | 수정 |
|---|---|
| H2 제거 뒤에도 Todo 엔티티가 남아 PostgreSQL validate 실패 가능 | API-000을 추가해 예제 제거를 PostgreSQL 전환보다 먼저 수행 |
| QA-002에 변경·전체 감사 endpoint 구현 선행 조건 누락 | API-011·API-013 의존 명시 |
| 미래 QA 완료를 이전 구현 승인 조건으로 삼으면 절차상 교착 | 개별 브랜치 qa 리뷰와 후속 QA 회귀 티켓 구분 |
| 담당이 orchestra인 티켓의 자기 승인 규칙 충돌 | qa 또는 관련 담당의 독립 검토 후 orchestra 통합 결정 |
| 실제 푸시·원격 반영·검토 SHA 증거 부족 | 모든 티켓에 커밋·원격 푸시·qa 대상 SHA·머지·통합 검증 필드 추가 |
| 승인과 통합 완료가 구분되지 않음 | APPROVED 뒤 MERGED 상태 추가, 선행 조건은 원격 통합까지 확인 |
| API-014의 상세·타임라인·요약 범위가 큼 | summary를 API-015로 분리 |
| QA-003의 트랜잭션·수집·조회 검증 범위가 큼 | 수집·조회·커서 검증을 QA-005로 분리 |
| 대시보드만으로 최종 E2E를 시작하면 회원 상세 완료를 보장하지 않음 | ADM-009에 ADM-006·API-015 의존 명시 |
| READ 독립 검증·검색 쿼리 실행 계획 담당 불명확 | QA-005에 READ-01~02, API-013에 대표 데이터 EXPLAIN 검증 명시 |
| 공용 파일·상태 기록 수정 주체 충돌 | orchestra 상태 관리, infra 후속 gitignore, qa Playwright 설정 담당 명시 |
| 실제 원격 CI 확인 없이 최종 승인 가능 | INF-003에 실제 CI 결과 확인, 불가능 시 BLOCKED 명시 |

최초 계획 검토에서 기존 35개를 38개로 세분화했다. 당시 담당 수: orchestra 5, api 16, admin 9, infra 3, qa 5. 이후 실제 통합 검증에서 API-016(Bean 이름), ADM-010(Next Origin 정규화), API-017(CSRF 암묵 세션 전략), API-018(오류 requestId 중복)을 별도 티켓·브랜치로 추적해 총 42개가 됐다. 현재 상태는 [티켓 목록](tickets/README.md)과 [최종 인수 보고](mvp-acceptance.md)가 기준이다.

## 기능 배정 확인

- DB·로컬 환경: INF-001~002, API-001~004. Compose는 infra, 애플리케이션 설정·Flyway는 api.
- 인증·오류·수집: API-005~009, API-012, ADM-002~004.
- 회원: API-010~011, ADM-005~006.
- 감사 검색·상세·타임라인·본인 활동·요약: API-013~015, ADM-007~009.
- 실행 문서·CI·최종 인수: INF-002~003, ORC-005.
- 관리자 설정, SSE, Kafka/Outbox 및 대규모 부하 실험은 명세대로 후속 범위다. DATA_DELETE는 카탈로그에는 유지하지만 MVP에 삭제 API는 없다.

## 검증 범위와 현재 상태

티켓 ID·브랜치명 유일성, 선행 ID 존재·의존 그래프 비순환성, 문서 링크, 목록과 개별 티켓 일치, 명세 테스트 추적을 검사한다.
애플리케이션 테스트·CI는 실행하지 않았다. 모든 티켓은 TODO이며 문서·코드는 아직 커밋·푸시·머지하지 않았다. api/.git 제거만 사용자의 별도 요청으로 수행했다.
