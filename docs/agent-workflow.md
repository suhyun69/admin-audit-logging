# 에이전트 역할 및 작업 승인 절차

실제 배정 단위는 [티켓 목록](tickets/README.md)의 개별 MD이며, 각 티켓의 고정 브랜치명을 사용한다. 브랜치 생성·worktree·승인 후 통합은 [브랜치 전략](branch-strategy.md)을 따른다.

## 역할

### orchestra

구현 명세와 계획을 읽고 작업을 티켓 단위로 나눈다. 각 티켓에 담당, 목표, 수정 범위, 선행 작업, 입출력 계약, 완료 기준과 검증 명령을 명시한다.
api·admin·infra·qa에게 작업을 배정하고 응답을 받는다. 보고서뿐 아니라 실제 변경 내용과 테스트 결과를 확인한다. 계약 위반·회귀·증거 부족이 있으면 보완을 요청하고, 충족한 작업만 승인한다.
API 계약과 이벤트 카탈로그, 공통 오류·권한 정책의 최종 정합성을 관리한다. 진행 상태와 승인 근거를 작업 기록에 남긴다.

### api

`api/`의 기존 Spring Boot 구조를 기반으로 구현한다. PostgreSQL 연결 설정, Flyway 스키마·local 시드, 세션·CSRF·권한, 회원 API, 감사 수집·검색·트랜잭션 경계를 담당한다.
단위·ArchUnit·PostgreSQL 통합 테스트로 자신의 작업을 검증한다. API 계약 변경은 orchestra에 먼저 전달하고 admin과 합의된 계약을 사용한다.

### admin

`admin/`에 Next.js 애플리케이션을 생성하고 로그인, 공통 레이아웃, 회원 화면, Explorer, 타임라인, 대시보드를 구현한다.
BFF의 쿠키·CSRF 전달, API 클라이언트, 인증 캐시, CLIENT 이벤트 전송과 interactionId 전파를 담당한다. 타입 검사·lint·build 및 담당 프론트엔드 테스트 결과를 보고한다.

### infra

루트 `docker-compose.yml`의 PostgreSQL 17 서비스, 포트·볼륨·healthcheck와 환경변수 예제를 관리한다. 로컬 실행·종료 절차, 인프라 스크립트와 CI 구성을 담당한다.
API와 Admin은 기본적으로 호스트에서 실행한다. api 담당과 DB 접속 변수, admin 담당과 API origin 변수를 합의한다. DB 마이그레이션 SQL과 애플리케이션 기능은 각 구현 담당의 범위다.
Compose 설정과 기동 상태를 검증하고 데이터 볼륨 삭제는 일반적인 종료 절차에 포함하지 않는다.

### qa

명세의 테스트 목록과 MVP 완료 시나리오를 독립적으로 검증한다. 정상 응답뿐 아니라 실제 DB 변경·감사 기록·롤백·권한 차단·중복 방지·동시성 결과를 확인한다.
교차 계층 통합 및 Playwright E2E를 담당한다. 필요한 테스트 파일은 orchestra가 구현 담당과 소유 범위를 조정한 뒤 작성한다.
실패 항목은 재현 절차, 기대·실제 결과, 관련 근거와 함께 보고한다. 수정 후 재검증 결과를 orchestra에 전달한다. 제품 코드를 임의로 수정해 실패를 숨기거나 스스로 최종 승인하지 않는다.

## 작업 흐름

1. orchestra가 선행 계약과 작업 의존성을 확인하고 티켓을 작성한다.
2. 담당 에이전트가 배정 범위·완료 기준을 확인한 뒤 구현한다. 계약 충돌이나 범위 밖 변경은 orchestra에 보고한다.
3. 담당이 자체 검증 후 실제 커밋·원격 푸시하고 SHA·원격 브랜치와 결과를 제출한다.
4. orchestra가 실제 diff와 검증 증거를 확인한다. 교차 계층·보안·트랜잭션 작업은 qa 검증을 요청한다.
5. qa가 PASS / FAIL / NOT RUN을 구분해 결과를 보고한다.
6. orchestra가 승인하거나 수정 요청을 전달한다. 수정 후 필요한 검증을 다시 수행한다.
7. orchestra가 승인된 티켓을 integration에 실제 머지·푸시하고 통합 smoke 결과·머지 SHA를 기록한다. 이후 선행 작업을 바탕으로 다음 티켓을 진행한다. 최종 MVP는 전체 인수 조건을 확인한 뒤 승인한다.

상태: `TODO → IN_PROGRESS → IN_REVIEW → APPROVED → MERGED`. 수정 요청은 `IN_PROGRESS`로 되돌린다. 외부 조건으로 막힌 작업은 `BLOCKED`와 사유·해제 조건을 기록한다.

## 최초 배정 순서

1. orchestra: API·이벤트·권한·CSRF 계약과 작업 목록 확정.
2. infra: PostgreSQL Compose와 환경변수·실행 절차 구성.
3. api: 기존 템플릿 점검 → PostgreSQL/Flyway → 감사 기반 → 인증 → 회원 → 감사 API.
4. admin: 확정 계약을 기반으로 Next.js 기반·BFF → 인증 UI → 회원·수집 → Explorer.
5. qa: 초기부터 인수 기준을 정리하고 각 단계의 구현 결과 및 최종 E2E를 검증.

독립적인 준비 작업은 동시 진행할 수 있다. API·DB·BFF 같은 경계를 넘는 작업은 선행 계약과 실제 연동 검증을 거쳐 승인한다.

개별 티켓의 qa 리뷰는 해당 작업 브랜치에서 수행한다. QA-002~005는 통합 기능의 회귀 검증 티켓이므로 이전 구현 티켓의 승인 조건으로 역참조하지 않는다. 미래 기능 검증은 후속 티켓에서 수행할 범위를 명시하고, 현재 티켓의 필수 완료 기준 자체를 미검증인 채 승인하지 않는다.

상태 MERGED는 승인뿐 아니라 실제 머지·원격 integration 반영·통합 검증까지 완료했음을 뜻한다. 구현자는 보고 초안만 제출하고 orchestra가 상태와 목록을 갱신한다. ORC 티켓은 qa 또는 관련 담당의 독립 검토를 거친다. ORC-002가 루트 .gitignore 기준을 먼저 확보하고 INF-002가 후속 환경변수 제외 규칙을 확장한다. QA-004의 Playwright 설정과 E2E 스크립트 변경은 qa가 전담하며 admin은 해당 배정 기간에 같은 파일을 수정하지 않는다.
